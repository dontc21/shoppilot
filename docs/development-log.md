# ShopPilotBot 开发日志

本文只记录实际发生且能够说明证据来源的开发过程。由于项目在建立 Git 仓库前已经进行过若干实验，首次提交之前的内容属于“基线前开发记录”，不是由 Git commit 时间线恢复出的历史。

## 1. 项目初始化与拼多多接入尝试（2026-10-14）

### 开发目标

通过 Playwright 控制独立 Edge，复用店主手动登录状态，并持续读取客服网页而不自动发送消息。

### 问题表现

项目最初计划在店主手动登录后读取拼多多商家客服网页。接入期间，客服页面加载和真实 DOM 定位没有形成可复核的稳定结果；一次性 DOM 检测结束后，Playwright 控制的 Edge 还会随程序退出而关闭，不符合持续监听要求。

### 排查方法

- 检查浏览器上下文的创建与清理位置。
- 区分平台主动关闭、进程被终止和 Python 正常退出 Playwright 上下文。
- 将浏览器生命周期调整为持续循环，只在 `Ctrl+C` 或异常退出时清理 context。

### 观察证据

- 窗口关闭发生在检测脚本结束之后。
- 后续长驻模式能够让浏览器在检测完成后继续保持打开。
- 当前仓库未保留当时的拼多多平台代码或原始日志，因此不能从 Git 历史复原更细粒度证据，也不能判断页面加载异常的平台侧根因。

### 处理结果

确立了“持久化用户目录 + 手动登录 + 长驻监听 + 退出时清理”的浏览器生命周期设计。

### 实际修改

- 将浏览器启动方式确定为 `launch_persistent_context()`。
- 将一次性检测流程调整为持续运行，退出时才清理 Playwright context。
- 后续平台切换时没有保留拼多多专属定位器或运行配置，因此当前仓库无法逐行展示当时代码差异。

### 测试结果

当时没有留下可复核的自动化测试输出。只能确认后续长驻流程能够保持浏览器打开，不能据此声称拼多多消息读取已验证。

### 当前状态

拼多多接入已停止。相关配置和运行目录未进入当前项目基线；该阶段不构成已完成的平台接入。

## 3. 客服入口异常与 Playwright 诊断（2026-10-14）

### 开发目标

在不绕过登录或安全校验的前提下，确定“客服系统”点击后的页面创建、导航和失败阶段。

### 问题表现

店主点击商家后台顶部“客服系统”后，曾出现一个标题为“无标题”、地址停留在 `about:blank` 的新标签页。

### 排查方法

在店主再次手动点击前安装以下只读监听：

- BrowserContext `page`、`requestfailed`、`response`。
- Page `popup`、`framenavigated`、`console`、`pageerror`。
- 客服入口捕获阶段只记录标签、静态类名和链接行为。
- 网络日志只保留脱敏域名、路径、资源类型、状态码和错误类型。

### 观察证据

再次测试时：

- “客服系统”实际元素为由 JavaScript 事件代理处理的 `span`，不是普通链接。
- 捕获到一个 popup 和一个新页面。
- 客服主文档请求返回 HTTP 200。
- popup 主 frame 成功导航到客服页面。
- 点击后没有 console error、pageerror、requestfailed 或 HTTP 4xx/5xx。
- 页面加载过程中出现过子 frame 的临时 `about:blank`，但主页面最终成功加载。

### 处理结果

新增脱敏诊断工具，并让诊断完成后的 Edge 保持打开直到店主按 `Ctrl+C`。

### 实际修改

- `EntryDiagnosticRecorder.attach_context()`：监听新页面、失败请求和响应。
- `EntryDiagnosticRecorder.attach_page()`：监听 popup、frame 导航、console 和 pageerror。
- `EntryDiagnosticRecorder.inspect_entry()`：只检查客服入口的必要 DOM 结构。
- `run_diagnose_entry()`：在人工点击前安装监听，采集完成后继续保持 Edge 打开。

### 测试结果

- 真实页面诊断链路执行成功。
- 脱敏 URL、文本和嵌套值由 `tests/test_phase1.py` 覆盖。
- 原始 `about:blank` 故障未复现，根因未解决。

### 当前状态

**未解决 / 未复现。** 原始故障没有再次出现，根因尚未确定。不能将其描述为已解决的 Playwright 兼容性问题。若再次发生，应保留当次监听证据，不自动重复点击或猜测内部客服地址。

## 4. 消息监听与 SQLite 去重（2026-10-14）

### 开发目标

只读取店主当前打开的一个会话，识别新买家消息并在 SQLite 中跨重启去重，不发送消息。

### 问题表现

需要从真实客服页识别当前买家会话、买家消息、商家消息和稳定消息 ID，同时不得遍历其他真实买家或保存完整聊天记录。

### 排查方法

- 从 `context.pages` 查找已验证的客服主文档，而不是假设首页就是客服页。
- 增加 `probe-chat`，只围绕店主明确发送的“你好”采集脱敏 DOM 路径。
- 将读取范围限制为店主当前打开的一个会话，不自动点击会话列表。
- 优先使用平台消息 ID；缺失时使用多字段 SHA-256 回退指纹。
- SQLite 只保存消息哈希、脱敏会话键和首次观察时间。

### 观察证据

- 当前会话消息读取和 SQLite 去重骨架已编写，并有自动化测试覆盖。
- 2026-10-14 运行 Pytest，结果为 `13 passed`。
- `probe-chat` 已从 `context.pages` 识别真实客服页面。
- 店主打开测试买家会话后，程序观察到新增“你好”，并生成只含标签、类名和属性名的脱敏消息结构及 DOM 骨架。
- 脱敏结构确认当前会话项具有 `data-mid`，商家消息容器具有额外的反向布局类；消息正文和平台时间位于独立子节点。定位器热加载后在原浏览器进程内通过校验。
- 建立历史基线后，测试买家依次发送“你好1”和“你好2”。两条消息均只输出一次，且脱敏会话标识一致；第一条读取到平台时间，第二条因页面未提供独立时间而明确使用本地观察时间。
- 多个后续轮询周期没有再次输出这两条消息。SQLite 只读核验结果为 4 行、4 个唯一消息键、1 个会话，其中包含 2 条历史基线消息和 2 条新消息。

### 处理结果

已完成“结构探测 → 热加载真实定位器 → 建立基线 → 读取两条新消息 → 持续轮询去重”的当前会话闭环，全程保持 `DRY_RUN`。

### 实际修改

- `chat_probe.find_verified_chat_page()`：从 `context.pages` 选择真实诊断确认过的客服页。
- `chat_probe.capture_chat_probe()`：只围绕测试文本保存脱敏 DOM 路径。
- `BilibiliShopAdapter.read_messages()`：限制为当前会话，不自动遍历或点击其他买家。
- `message_key()`：平台 ID 优先；缺失时使用会话、正文、时间、方向和出现序号生成 SHA-256。
- `ProcessedMessageStore.add_if_new()`：利用 SQLite 主键实现跨进程去重。
- `listen()`：建立历史基线，只打印后续首次观察到的买家消息。
- `config/selectors.example.json`：保存本次真实页面验证得到的客服页、当前会话、正文、时间和方向定位器。
- `tests/test_phase1.py`：验证公开的定位器示例能够被安全加载。

### 测试结果

Python 3.11.9 下运行 `python -m pytest -q`，提交前结果更新为 `14 passed`。B站后台登录、客服页面导航、当前会话识别、两条不同买家消息读取以及同一进程持续轮询去重已完成真实验证。

### 当前状态

阶段一的当前会话实时读取和同进程去重验收通过。真实 DOM 未发现稳定平台消息 ID，回退组合指纹可能受页面排序、时间字段格式和同文本出现序号变化影响。真实重启后的去重随后在第二阶段验证通过。

## 6. 安全测试发送（2026-10-14）

### 开发目标

在不开放自动回复和批量发送的前提下，只向店主自己的测试买家会话发送一条固定回复，并验证会话隔离、发送结果和重复保护。

### 发送前验证与证据

- 正常停止旧监听并重新启动持久化 Edge。当前会话可见 4 条历史消息，SQLite 全部识别为已处理，新加入基线为 0；真实跨重启去重验证通过。
- 测试买家发送“方向测试-买家”后识别为买家消息；店主在商家网页手动回复“方向测试-商家”后识别为商家自己发送。两条消息的脱敏会话标识一致，后续轮询没有重复输出。
- 当前选中会话具有稳定的 `data-mid`。发送流程只在内存中使用原始值做精确比较，终端只显示 SHA-256 前缀形成的脱敏会话标识。
- 脱敏 DOM 证据确认输入框为 `textarea#chat-textarea`，发送按钮为当前输入区唯一的主按钮；这些定位器写入公开示例配置，不保存动态属性值或聊天记录。

### 实际修改

- `BilibiliShopAdapter.send_message()`：发送前、填写后和点击后反复校验当前 `data-mid`；只点击一次，并根据新增的同文本商家消息返回 `SENT` 或 `UNKNOWN`。
- `OneTimeTestSendPermit`：将授权绑定到确定会话与确定正文，消费后不可复用。
- `OutgoingMessageStore`：只保存请求哈希、会话哈希、正文哈希和 `PREPARED`、`SENT`、`UNKNOWN` 或 `ABORTED` 状态；已有记录时禁止重复点击。
- `shoppilotbot.stage2 verify`：只读验证跨重启去重及买家/商家方向。
- `shoppilotbot.stage2 send-test`：先输出 `DRY_RUN` 预览，再要求含随机码的一次性授权短语；只允许固定测试回复。
- `config/selectors.example.json`：增加输入框和发送按钮的真实 DOM 定位器。
- `tests/test_phase1.py`：增加一次性授权、会话绑定、发送记录持久化、重复保护和中文短语比较测试。

### 重要 Bug：中文授权短语比较失败

- 问题表现：第一次输入正确授权短语后，程序在发送前抛出 `TypeError` 并退出。
- 根因及证据：`secrets.compare_digest()` 的字符串模式只支持 ASCII，而授权短语包含中文“会话”。堆栈定位到 `stage2.py` 的授权比较行。
- 安全影响：异常发生在 SQLite 发送预约、输入框填写和按钮点击之前，能够确认此次没有发送，不属于结果未知。
- 修复方法：`confirmation_matches()` 将两侧字符串编码为 UTF-8 字节后再比较，并加入非 ASCII 回归测试。
- 验证结果：修复后自动化测试为 `18 passed`，新进程生成新的随机授权；旧授权没有复用。

### 真实发送验收

- `send-test` 先输出目标会话、固定正文和 `DRY_RUN` 状态，确认未填写、未点击。
- 店主原样确认新的随机一次性短语后，程序只点击一次发送。
- 页面出现新增的同文本商家消息，程序记录 `SENT`。
- 对相同会话和正文再次预约时，SQLite 在点击前阻止重复请求。
- 店主在自己的买家测试账号确认收到 `ShopPilotBot 测试回复，请忽略。`。
- 提交前最终运行 `python -m pytest -q`，结果为 `19 passed`。

### 当前状态

单条固定测试回复的安全发送闭环已完成真实平台验收。自动回复、批量发送和 DeepSeek Agent 仍未开放；`UNKNOWN` 防重试分支尚未在真实平台故意制造异常验证。

## 7. SQLite 商品知识库与 DeepSeek Agent（2026-10-14）

### 开发目标

使用人工输入的模拟商品问题验证“模型选择工具 → Python 查询 SQLite → 模型生成候选回复 → Python 独立决策”流程。本阶段不读取真实买家消息，不连接浏览器发送链路。

### 安全边界与实现

- `knowledge.KnowledgeBase`：建立商品、FAQ 和售后规则三张表，保留知识来源、更新时间、批准状态和模拟数据标记。
- `KnowledgeBase.import_json()`：校验固定 JSON 结构后导入；相同 ID 明确更新，搜索内容全部通过 SQL 参数绑定。
- `KnowledgeBase.search_knowledge()`：只查询代码内固定的表和列，最多返回 8 条证据；模型不能提交任意 SQL。
- `DeepSeekChatClient`：调用 Chat Completions API，限制 HTTPS 地址、请求超时、响应大小和最多 800 个输出 Token；不记录密钥或请求正文。
- `CustomerServiceAgent.answer()`：第一轮强制请求 `search_knowledge`，最多接受一次工具调用；Python 验证工具名、参数白名单和范围，再将本地结果交给第二轮生成结构化候选回复。
- `DecisionRules.evaluate()`：独立检查高风险事项、证据 ID、知识批准状态、未授权承诺和证据中不存在的数字。模型置信度不参与决策。
- `TokenUsage`：累计两轮 API 返回的输入、输出、缓存命中和缓存未命中 Token，便于控制费用；不记录请求正文或密钥。
- `agent_cli`：只处理人工输入的模拟问题，输出候选回复、状态、证据 ID、审核原因和工具轨迹；没有浏览器发送入口。
- `examples/sample_knowledge.json`：只包含明确标记为模拟的虚构商品、FAQ 和规则，不代表真实店铺资料。

### 测试证据

- 使用临时 SQLite 数据库和本地假模型测试完整的两轮 Tool Calling 数据流，没有向外部 API 发送内容。
- 已知材质问题和同义表达能够得到 `AUTO_REPLY_CANDIDATE`。
- 未知知识、退款/赔偿、API 超时或错误、模型不调用工具、无效 JSON、引用工具结果之外的证据、未授权质保承诺和无依据数字均得到 `NEED_REVIEW`。
- SQL 注入形式的搜索文本没有改变数据库表，导入缺少版本号的 JSON 会被拒绝。
- 修复并增加回归测试后运行 `python -m pytest -q`，结果为 `37 passed`，其中包含此前 19 项浏览器读取与发送安全测试。
- 实际执行模拟 JSON 导入和本地检索命令，导入 1 个商品、2 条 FAQ 和 1 条规则，能够返回带来源和更新时间的证据。

### 真实 DeepSeek API 验收

验收只使用 `examples/sample_knowledge.json` 和人工输入的模拟问题，没有传输真实买家消息、订单信息或个人信息。

- 已知问题“星云随行杯是什么材质”：模型调用 `search_knowledge`，查询词为“星云随行杯 材质”；Python 实际查询 SQLite 并返回商品及 FAQ 证据，最终状态为 `AUTO_REPLY_CANDIDATE`。
- 同义问题“这个杯子的杯身是什么做的”：模型调用相同工具并生成“杯子 杯身 材质”查询；SQLite 返回材质 FAQ，最终状态为 `AUTO_REPLY_CANDIDATE`。
- 高风险问题“我要退款并要求赔偿”：Python 在调用模型前返回 `NEED_REVIEW`，工具轨迹为空，Token 用量为 0。

### 真实验收发现：知识缺失仍被候选放行

- 问题表现：询问模拟资料中不存在的“无线充电”能力时，工具因商品名命中返回了该商品的其他资料。模型正确说明“资料未提及”，但旧规则只验证证据 ID 和危险承诺，错误输出 `AUTO_REPLY_CANDIDATE`。
- 根因证据：真实工具轨迹显示查询词为“星云随行杯 无线充电”，返回的是材质和容量证据，没有无线充电事实；候选回复包含“未提及”，旧规则仍显示通过。
- 修复方法：在 `DecisionRules.evaluate()` 增加知识不足表达门禁，并要求模型在证据不能明确回答时写出“无法确认”。新增 `test_product_hit_does_not_approve_missing_fact()` 回归测试。
- 验证结果：自动化测试更新为 `37 passed`。真实 API 使用相同未知问题复测，模型调用 SQLite 后输出“无法确认”，Python 独立决策为 `NEED_REVIEW`。

### Token 与费用

## 8. 后续开发记录规范

1. 以“真实、可独立验证的功能”“重要 Bug”或“开发里程碑”为日志单位；合并同一功能的细微调整，避免按命令或工具调用记流水账。
2. 功能记录应包含开发目标、核心文件或函数、技术原理、验证方式、真实测试结果和当前限制。
3. 重要 Bug 记录问题表现、排查证据、已确认根因、修复方法及验证结果。根因不确定时写“未解决”，后续无法重现时写“未复现”。
4. 严格区分代码已实现、自动化测试通过和真实平台验收通过；只有实际完成对应测试后才能更新状态。
5. 每次 Git Commit 前检查日志。重要功能、修复或里程碑应与相关代码和测试放在同一逻辑提交中；纯格式或微小调整可以不更新日志。
6. 不为增加提交数量拆分功能，不伪造提交时间、开发过程、Bug 原因或测试结果。
7. 每次开发完成后向店主报告完成内容、核心文件、实际测试、未解决问题、Commit Message 和 Commit Hash。
8. 禁止将 Cookie、Token、API Key、真实买家隐私、浏览器登录配置、运行数据库和敏感调试数据写入日志或提交到 GitHub。
